Sparse Matrices & Large Systems

Physics couples each point only to its neighbors — so the matrices are almost all zeros, and learning not to store those zeros is what lets you simulate a million-atom system on a laptop.

🎯 Learning Objectives

  • Explain why matrices from physics simulations are sparse: discretized operators couple each site only to its local neighbors.
  • Quantify the memory and arithmetic cost of dense storage and see why it explodes for large systems.
  • Read and reason about the Compressed Sparse Row (CSR) format and its three arrays.
  • Use SciPy's scipy.sparse to build, store, and multiply sparse matrices.
  • Recognize the sparse matrix–vector product (SpMV) as the single operation iterative solvers repeat — and the gateway to next week's Krylov methods.

6.1Why Physics Matrices Are Almost All Zeros

When you discretize a physical operator — a Laplacian for a diffusion problem, a Hamiltonian for a quantum lattice, a stiffness matrix for a vibrating structure — you place the system on a grid or a mesh of N sites. The matrix A that results has one row and one column per site. Its entry Aij answers a physical question: how strongly does site i couple to site j?

The crucial fact is that physics is local. A particle on a lattice hops to adjacent sites; heat flows between touching cells; a spring connects only the masses it is attached to. A site couples to a handful of neighbors and to nothing else. So in row i, only a few entries are nonzero and the rest — the overwhelming majority — are exactly zero.

Take the standard second-derivative (1-D Laplacian) operator. The finite-difference rule

f''(xi) ≈ [ fi-1 - 2 fi + fi+1 ] / h2Each grid point talks only to its immediate left and right neighbor, so each matrix row has at most three nonzeros.

produces a tridiagonal matrix: nonzeros only on the main diagonal and the two adjacent diagonals. Out of N2 entries, only about 3N are nonzero. We call a matrix sparse when the number of nonzeros, nnz, grows like N rather than N2 — formally, when the fraction of nonzeros vanishes as the system grows.

AnalogyThink of a class seating chart where you record who each student can pass a note to. They can only reach the people sitting right next to them. The full "who-can-reach-whom" table for 1000 students has a million cells, but every row has just two or three names in it. Writing out all 997 "no" entries per row is a colossal waste of paper — you would only ever list the few neighbors. A sparse matrix format does exactly that.

6.2The Cost of Storing Zeros

A dense matrix stores every entry, so it needs N2 numbers. In IEEE 754 double precision each number is 8 bytes, giving:

dense memory = 8 N2 bytesFor N = 100,000 this is 8 × 1010 bytes = 80 GB — already impossible on a laptop, and we have not done any arithmetic yet.

The quadratic growth is brutal. A 3-D simulation on a modest 200×200×200 grid has N = 8×106 unknowns; the dense matrix would need 8N2 ≈ 5×1014 bytes — half a petabyte — to hold a matrix that is more than 99.9999% zeros. A dense matrix–vector multiply costs 2N2 floating-point operations, and a dense direct solve (LU/Gaussian elimination) costs about (2/3)N3 — both hopeless at this scale.

Sparse storage keeps only the nonzeros and their locations. If each row has a fixed handful of nonzeros (call it the bandwidth or stencil size k), then:

sparse memory ≈ (8 + 4) · nnz ≈ 12 k N bytes  (linear in N)8 bytes for each value, ~4 bytes for each column index. Cost grows like N, not N2.

For the 8-million-site grid with k ≈ 7 nonzeros per row, that is roughly 12 × 7 × 8×106 ≈ 0.7 GB — it fits in memory, and a sparse multiply costs only about 2·nnz ≈ 108 operations instead of 1014. The same shift turns the impossible into the routine.

Common mistakeDo not build a dense matrix and then convert it to sparse — you will run out of memory at the dense step, before the conversion ever runs. The whole point is to never materialize the N×N array. Build sparsely from the start (e.g. with diagonals or coordinate triplets) and assemble directly into a sparse format. Likewise, never call a dense solver like numpy.linalg.solve on a problem big enough to need sparsity.

6.3Compressed Sparse Row (CSR)

The most widely used sparse format is Compressed Sparse Row (CSR). It throws away every zero and stores the matrix in three flat arrays:

  • data — the nnz nonzero values, listed row by row.
  • indices — the column index of each value in data (same length, nnz).
  • indptr — length N+1. Entry indptr[i] is where row i's values begin in data; the nonzeros of row i are the slice data[indptr[i] : indptr[i+1]].

The indptr ("index pointer") array is the clever part: instead of storing a row index for every nonzero, it stores N+1 boundaries, so the number of nonzeros in row i is simply indptr[i+1] - indptr[i]. Total storage is 2·nnz + N + 1 numbers — linear in the size of the problem.

Related cousins exist: CSC (compressed sparse column, the same idea transposed) is efficient for column operations; COO (coordinate format: parallel arrays of row, column, value) is the easiest to build and is usually converted to CSR for fast arithmetic. SciPy lets you assemble in one format and convert in a single call.

6.4The Sparse Matrix–Vector Product (SpMV)

Why is CSR organized by rows? Because the single most important operation on a large sparse matrix is the matrix–vector product y = A x, and in CSR each output entry is a tidy row-slice dot product:

yi = sum over the nonzeros in row i of Aij xjIn CSR: for k from indptr[i] to indptr[i+1]-1, accumulate data[k] * x[indices[k]].

This costs only about 2·nnz floating-point operations — proportional to the number of nonzeros, not to N2. For a tridiagonal matrix that is ~6N operations: a million-row multiply is a few million flops, done in well under a millisecond.

Here is the decisive point for the rest of this course: iterative solvers and eigensolvers never need the matrix itself — only the ability to compute A x for an arbitrary vector x. Conjugate Gradient, GMRES, and the Lanczos and Arnoldi algorithms (next week) all build their answer from a sequence of SpMV calls. The matrix can even stay implicit — defined only by a function that returns A x — which is exactly what SciPy's LinearOperator abstraction allows.

work per iteration ≈ SpMV cost ≈ O(nnz)  →  total ≈ O(nnz · iterations)Replace the O(N3) of a dense solve with O(nnz) per iteration; for well-conditioned sparse systems the iteration count is modest.
AnalogyAn iterative solver is like finding your way through a city by only ever asking "which streets leave this intersection?" You never need a printed map of every road in the country (the dense matrix) — you just need a rule that, given where you stand, tells you your immediate neighbors. SpMV is that rule, and Krylov methods are the strategy for walking it efficiently toward the destination.
✦ Worked Example — CSR storage and a multiply by hand

Take the 4×4 matrix from the figure and compute y = A x by hand using its CSR arrays, with x = [1, 1, 1, 1]T.

  1. The matrix: row 0 = [5,0,0,2], row 1 = [0,8,0,0], row 2 = [3,0,4,0], row 3 = [0,0,0,7]. There are nnz = 6 nonzeros.
  2. CSR arrays: data = [5,2,8,3,4,7], indices = [0,3,1,0,2,3], indptr = [0,2,3,5,6]. Storage = 2·6 + (4+1) = 17 numbers vs 16 dense — no savings at this toy size, but linear growth at scale.
  3. Row 0 uses data[0:2] = [5,2] at columns [0,3]: y0 = 5·x0 + 2·x3 = 5 + 2 = 7.
  4. Row 1 uses data[2:3] = [8] at column [1]: y1 = 8·x1 = 8.
  5. Row 2 uses data[3:5] = [3,4] at columns [0,2]: y2 = 3·x0 + 4·x2 = 3 + 4 = 7.
  6. Row 3 uses data[5:6] = [7] at column [3]: y3 = 7·x3 = 7.
  7. Result: y = [7, 8, 7, 7]T, computed with exactly 2·nnz = 12 multiply-adds and without ever touching a single one of the 10 zero entries.

🛠️ Hands-On: build a Laplacian sparsely and watch it scale

This uses the free Python + NumPy + SciPy stack you set up in Week 1 (see the install details in Lecture 1 of Course 1). We lean on scipy.sparse here — it ships with SciPy, so there is nothing new to install. We build the 1-D Laplacian with diags, confirm it is stored as CSR, and compare memory and SpMV time against the dense version as N grows.

# sparse_laplacian.py — Lecture 6
import numpy as np
import scipy.sparse as sp
import time

def laplacian_1d(N):
    # tridiagonal: -2 on the diagonal, +1 on the off-diagonals
    main = -2.0 * np.ones(N)
    off  =  1.0 * np.ones(N - 1)
    A = sp.diags([off, main, off], offsets=[-1, 0, 1], format="csr")
    return A

A = laplacian_1d(8)
print(A.toarray())            # peek at the small dense form
print("nnz =", A.nnz)         # 22 for N=8 (3N - 2)
print("format:", A.getformat(), "| indptr:", A.indptr)

# the key operation: sparse matrix-vector product
x = np.ones(8)
print("A @ x =", A @ x)       # interior rows give 0, ends give -1

# memory + speed: sparse stays linear, dense blows up
for N in [1_000, 10_000, 100_000]:
    A = laplacian_1d(N)
    x = np.random.rand(N)
    sparse_mb = (A.data.nbytes + A.indices.nbytes + A.indptr.nbytes) / 1e6
    dense_mb  = 8 * N * N / 1e6
    t0 = time.perf_counter(); _ = A @ x; t = time.perf_counter() - t0
    print(f"N={N:>7}: sparse={sparse_mb:7.3f} MB  dense={dense_mb:12.1f} MB  SpMV={t*1e3:.3f} ms")
# dense memory grows as N^2 (80 GB at N=100k); sparse grows as N (~1 MB)

Try wrapping the action x -> A @ x in scipy.sparse.linalg.LinearOperator and pass it to scipy.sparse.linalg.cg to solve A·u = b without ever forming a dense matrix — a preview of next week. Predict the SpMV time at N = 106 before you run it (hint: it scales linearly).

🔗 Where this is heading

Sparsity is the hinge that the rest of this course swings on. Next week the Lanczos and Arnoldi (ARPACK) methods compute a few eigenvalues of a giant sparse Hamiltonian using nothing but repeated SpMV calls — the way real quantum-lattice and band-structure calculations find ground states. In Course 4, every implicit PDE time-step and every Poisson solve assembles a sparse operator and hands it to an iterative solver, often with a preconditioner to cut the iteration count. The same sparse machinery underlies large-scale optimization in the Quant track and the giant linear systems of plasma and structural simulations. Master "store only the couplings, and only ever multiply" now, and million-unknown physics becomes a laptop-sized problem.

💬 Discussion

A colleague hands you a working dense-matrix simulation of a 1-D quantum well: it builds the N×N Hamiltonian, calls a dense eigensolver for the ground state, and runs fine at N = 2,000. They now want N = 2,000,000 to resolve fine spatial detail, and they ask you whether they "just need a bigger machine." How would you explain what actually breaks, what stays cheap, and what they should change? In your answer, distinguish the storage problem from the algorithm problem, and say which single operation their new code must be built around.

Show a model response

A bigger machine cannot save them, because both costs grow super-linearly. Storage: a dense N×N matrix needs 8N2 bytes. At N = 2×106 that is 8 × (2×106)2 = 3.2×1013 bytes ≈ 32 TB — no single machine holds it. But the Hamiltonian of a 1-D well is tridiagonal: only ~3N ≈ 6×106 nonzeros, which in CSR is only tens of megabytes. So the matrix itself is not the problem — storing its zeros is.

There are really two separate problems. The storage problem is solved by switching to a sparse format (build it with scipy.sparse.diags, never materialize the dense array). The algorithm problem is that a dense eigensolver costs O(N3) and returns all N eigenpairs — wasteful when they only want the ground state. The fix is an iterative eigensolver (Lanczos / ARPACK via scipy.sparse.linalg.eigsh) that finds just the few lowest states.

The single operation their new code must be built around is the sparse matrix–vector product A x, costing O(nnz). Every iterative eigensolver and linear solver is just a smart sequence of those products; the matrix can even stay implicit behind a LinearOperator. So: switch to sparse storage, switch to an iterative solver that asks only for the few states they want, and make SpMV the core primitive.

✓ Self-check rubric. A strong answer (1) names the 8N2 dense-memory blow-up with a concrete number, (2) separates the storage fix (sparse/CSR) from the algorithm fix (iterative eigensolver returning only a few states, not O(N3) for all of them), and (3) identifies the sparse matrix–vector product as the central O(nnz) operation everything is built on.

5 questions · click "Show answer" to check yourself.

Q1. Matrices that arise from discretizing physical operators (Laplacians, lattice Hamiltonians, stiffness matrices) are typically sparse because…
A. physical couplings are local, so each site interacts with only a few neighbors
B. floating-point round-off forces most entries to exactly zero
C. the matrices are always diagonal
D. sparsity is an arbitrary choice with no physical basis
Show answer

A. Locality of physics (a site couples only to its neighbors) makes most off-diagonal entries exactly zero. B confuses sparsity with round-off — the zeros are structural, not numerical. C is false (a tridiagonal Laplacian is not diagonal). D ignores the physical origin.

Q2. A dense N×N matrix in double precision needs 8N2 bytes. Roughly how much memory is that for N = 100,000?
A. about 80 MB
B. about 80 GB
C. about 800 KB
D. about 8 GB
Show answer

B. 8 × (105)2 = 8 × 1010 bytes = 80 GB. A and C ignore the quadratic N2 term; D is off by a factor of ten. The sparse version of the same operator would be only a few MB.

Q3. In CSR format, what is stored in the indptr array?
A. the value of every nonzero entry
B. the column index of every nonzero entry
C. the per-row boundaries: where each row's nonzeros begin and end in data
D. the row and column of every nonzero, stored as pairs
Show answer

C. indptr has length N+1 and marks where each row starts in data; row i's nonzeros are data[indptr[i]:indptr[i+1]]. A is data; B is indices; D describes the COO (coordinate) format, not CSR's compressed pointers.

Q4. For a sparse matrix with nnz nonzeros, the cost of one matrix–vector product A x is about…
A. O(N3)
B. O(N2)
C. O(log N)
D. O(nnz), i.e. proportional to the number of nonzeros
Show answer

D. SpMV touches each nonzero once with a multiply-add, so the cost is ~2·nnz = O(nnz). A is a dense direct solve; B is a dense multiply; C is far too optimistic — you must at least read every nonzero.

Q5. Why are iterative solvers (Conjugate Gradient, GMRES) and iterative eigensolvers (Lanczos/ARPACK) natural partners for sparse matrices?
A. they require the matrix only through repeated matrix–vector products, which are cheap and sparse-friendly
B. they need the full inverse of the matrix computed up front
C. they only work on diagonal matrices
D. they convert the sparse matrix to dense form before solving
Show answer

A. Krylov methods build their answer from a sequence of SpMV calls, each O(nnz), so they exploit sparsity perfectly — the matrix can even stay implicit behind a LinearOperator. B (forming an inverse) and D (densifying) destroy sparsity; C is false (they handle general sparse matrices).

✓ What you learned

  • Physics matrices are sparse because couplings are local: each discretized site touches only a few neighbors, so nnz grows like N, not N2.
  • Dense storage costs 8N2 bytes and dense solves cost O(N3) — both explode; sparse storage and SpMV are linear in N.
  • CSR packs a matrix into three arrays — data, indices, indptr — storing only nonzeros and per-row boundaries.
  • SciPy's scipy.sparse builds and multiplies sparse matrices directly, without ever materializing the dense array.
  • The sparse matrix–vector product (SpMV), costing O(nnz), is the single operation every iterative solver and eigensolver repeats.
