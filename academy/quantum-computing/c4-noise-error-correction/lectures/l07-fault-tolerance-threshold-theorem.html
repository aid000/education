Week 7 · Lecture 7

Fault Tolerance & the Threshold Theorem

The surface code can be scaled bigger. But does bigger always mean better? The threshold theorem answers precisely when scaling helps — and when it backfires.

🎯 Learning Objectives

  • State the threshold theorem's conclusion: below a critical physical error rate, scaling a code suppresses the logical error rate arbitrarily low.
  • Explain the intuition for why a threshold exists at all (error correction itself introduces more operations, hence more opportunities for error).
  • Cite realistic threshold estimates (roughly 10⁻³–10⁻² depending on the code and architecture).
  • Explain why current NISQ devices sit close to, but not safely below, this threshold.
  • Connect the threshold theorem's "arbitrarily low logical error" promise to why large-scale fault-tolerant quantum computing is believed possible in principle.

7.1The Catch: Error Correction Itself Isn't Free

Weeks 4–6 built codes that detect and fix errors. But look closely at what that correction cycle actually costs: extra qubits, extra CNOTs for syndrome extraction, extra measurements — more operations, each one its own opportunity for a fresh error. Scale the surface code bigger (Lecture 6's trade-off) and you also scale up the total number of noisy operations per correction cycle. The obvious worry: does error correction eventually make things worse, not better?

7.2The Threshold Theorem

The threshold theorem answers that worry precisely. Its conclusion: there exists a critical physical error rate — the threshold, p_th — such that if your actual physical gate error rate p is below p_th, then scaling up the code (more qubits, more levels of concatenation or a larger lattice) drives the logical error rate down, arbitrarily close to zero. If p is above p_th, scaling up makes things worse instead of better.

p < p_th  ⟹  logical error rate → 0 as code size growsThis is the entire reason large-scale, fault-tolerant quantum computing is believed to be possible in principle, rather than a hope resting on finding "perfect" hardware.

The intuition: below threshold, each additional layer of error correction suppresses errors by more than it introduces — net progress. Above threshold, the new errors introduced by the correction machinery outpace what gets fixed — net regression, and the "cure" is worse than the disease. This course won't derive the theorem (that proof is well beyond a 10-week intro), but the conclusion above is the single most important fact in the entire field of fault-tolerant quantum computing.

7.3Realistic Threshold Numbers — and Where NISQ Sits

Depending on the specific code and hardware architecture, realistic threshold estimates fall roughly in the range p_th ≈ 10⁻³ to 10⁻² (one error in a thousand to one error in a hundred, per physical operation). That sounds achievable — and it's exactly why fault tolerance is a serious engineering target, not science fiction.

Honest framingToday's best NISQ hardware runs two-qubit gates at error rates often in the 10⁻³ ballpark — meaning current devices are frequently close to estimated thresholds, sometimes even nominally below them for the best gates, but nowhere near safely and consistently below threshold across every operation (idle qubits, readout, crosstalk, and calibration drift all add their own error budgets). "Close to threshold on your best gate" is a very different claim from "safely fault-tolerant at scale." This gap — not a missing theorem, but a missing margin of engineering safety — is exactly why Week 8 turns to what today's actual hardware numbers look like.
✦ Worked Example — reading the threshold qualitatively

Two research groups report physical gate error rates of p_A = 2×10⁻³ and p_B = 2×10⁻², against an estimated threshold of p_th ≈ 10⁻². Which group benefits from building a bigger code, and which should not?

  1. Compare p_A to p_th: 2×10⁻³ = 0.002, versus p_th = 0.01. Since p_A < p_th, Group A is below threshold.
  2. Compare p_B to p_th: 2×10⁻² = 0.02, versus p_th = 0.01. Since p_B > p_th, Group B is above threshold.
  3. Apply the theorem to Group A: below threshold — scaling up their code (bigger lattice, more concatenation levels) will drive their logical error rate down, arbitrarily close to zero, as predicted.
  4. Apply the theorem to Group B: above threshold — scaling up their code will make the logical error rate worse, not better. Group B's priority must be reducing their physical gate error rate first — more qubits is the wrong fix.
  5. Takeaway: "Add more qubits and more error correction" is only a win below threshold. Above it, the right move is improving the physical hardware itself — exactly the tension Week 8's real device numbers will make concrete.

🔗 Where this is heading

The threshold theorem is a promise about what's possible in principle. Week 8 grounds that promise in today's actual hardware: real gate error rates, real T1/T2 numbers, real readout error — and an honest look at why "below threshold in principle" hasn't yet translated into "fault-tolerant at scale in practice," which is exactly why error mitigation (Week 9) matters so much for the NISQ era specifically.
