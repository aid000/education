Week 7 · Lecture 7

Building Agentic Workflows

Last week you met the agent loop. This week you turn it into a reliable pipeline — chaining steps, adding tools and memory, scoring outputs, and keeping a human at the wheel.

🎯 Learning Objectives

  • Decompose a goal into a multi-step pipeline and decide when to chain prompts versus loop an agent.
  • Explain how tools and retrieval (RAG) give a model access to actions and fresh, grounded facts.
  • Distinguish a model's context window from external memory & state, and know when to use each.
  • Build a lightweight evaluation ("eval") loop so you can measure whether a workflow actually works.
  • Place human-in-the-loop checkpoints where the cost of a wrong action is high.

7.1From One Prompt to a Pipeline

A single prompt answers a single question. Real work is rarely one question — it is a sequence: gather information, transform it, check it, format it, deliver it. An agentic workflow is that sequence made explicit, with a model driving one or more of the steps.

There are two ways to structure the sequence, and choosing correctly is the first design decision:

  • Prompt chaining — you, the designer, fix the steps in advance. Step 1's output is piped into step 2's input, and so on. The path is deterministic: every run takes the same route. Best when you already know the recipe (e.g. "summarize → translate → format as a table").
  • Agent loop — the model decides the next step at runtime, choosing tools and repeating until the goal is met (the perceive → plan → act loop from Week 6). The path is dynamic: it adapts to what it finds. Best when the steps depend on intermediate results (e.g. "research this topic" — you don't know in advance how many searches it will take).

A good rule: use the simplest structure that works. Chaining is cheaper, faster, and far easier to debug because it has no surprises. Reach for a full agent loop only when the task genuinely needs the model to decide its own path.

7.2Tools & Retrieval — Giving the Model Hands and Fresh Eyes

A bare language model can only emit text from what it learned during training. It cannot run code, search today's web, or read your files. Tools close that gap: you describe a function (its name, what it does, and the arguments it takes), and the model can decide to call it. The system runs the function and feeds the result back into the model's context. This is the "act" step of the agent loop made concrete.

The most common and most useful tool is retrieval — fetching relevant text and inserting it into the prompt so the model can answer from grounded sources rather than memory. The standard pattern is RAG (Retrieval-Augmented Generation):

query → retrieve relevant chunks → (chunks + query) → model → grounded answerThe model answers using text you supplied this turn, not just its training weights — which reduces hallucination and lets it cite sources.

Retrieval usually works by embeddings (the meaning-vectors from Week 2): your documents are split into chunks, each chunk is turned into a vector and stored, and at query time you find the chunks whose vectors are closest to the query's vector. "Closest" is typically measured by cosine similarity:

similarity(a, b) = (a · b) / (‖a‖ ‖b‖)  ∈ [−1, 1]1 = same direction (very similar meaning), 0 = unrelated. The top-k highest-scoring chunks get pasted into the prompt.
AnalogyA model with no tools is a brilliant expert locked in a room with no phone and no calendar — they know a lot, but nothing about today and can't act on the world. Giving it tools is handing that expert a phone, a search engine, and a notepad. RAG is specifically handing them the exact three pages of the manual they need, instead of asking them to recall the whole manual from memory.

7.3Memory & State — What the Model Forgets

A model has no built-in memory between calls. Everything it "knows" in a given turn is whatever sits inside its context window — the chunk of tokens you send it. When the conversation grows past that window, the oldest content falls out and is simply gone. To a fresh API call with no history, the model is a stranger meeting you for the first time.

So a workflow that needs to remember things must store them outside the model and re-supply them when relevant. It helps to separate two kinds:

  • Short-term memory (state): the running scratchpad of this task — the conversation so far, intermediate results, what tools have been tried. Lives in the context window or a small variable you re-paste each turn.
  • Long-term memory: facts that should persist across sessions — your preferences, a knowledge base, past decisions. Stored in a database or vector store and retrieved (Section 7.2) when relevant, never kept in context all at once.
Common mistakeTwo failure modes to watch. (1) Assuming the model "remembers" across separate API calls — it does not; if you didn't re-send it, it's gone. (2) Stuffing everything into context "just in case." A bloated context is slower, costs more, and can actually lower accuracy — models can lose track of facts buried in the middle of a very long prompt (the "lost in the middle" effect — as of 2026, hedge: the exact severity varies by model and is worth re-checking against current evaluations). Retrieve what's relevant; don't dump the whole archive.

7.4Evaluation — How Do You Know It Works?

A demo that works once proves nothing. Because models are probabilistic — the same prompt can give different answers — the only way to trust a workflow is to measure it across many cases. That measurement is called an eval.

An eval is simply: a set of test inputs, a way to score each output, and a number you can track as you change the prompt or pipeline. Scoring methods, from cheapest to richest:

  • Exact / programmatic checks — does the output equal the known answer, parse as valid JSON, contain the required field? Cheap, objective, best where there's a right answer.
  • Heuristics — length, presence of keywords, passes a regex. Crude but catches obvious failures.
  • LLM-as-judge — a second model grades the output against a rubric ("Is this answer grounded in the sources? Score 1–5"). Useful for open-ended tasks, but the judge can be wrong, so spot-check it against human judgment.
  • Human review — the gold standard, the most expensive. Use it to validate the cheaper methods and on a sample of real traffic.

The simplest useful score is accuracy over a test set:

accuracy = (# outputs that pass) / (total test cases)Run it before and after every change. If a "clever" new prompt drops accuracy, you just learned something a single demo never would have told you.

7.5Keeping a Human in the Loop

Autonomy is a dial, not a switch. The more a workflow can act on the world — send emails, spend money, delete files, publish content — the higher the cost of a confident mistake. Human-in-the-loop (HITL) design means placing approval checkpoints exactly where that cost is high, and letting the agent run freely where it is low.

A practical way to decide is a quick risk grid: how reversible is the action, and how large is the impact?

Common HITL patterns: approval gates (the agent proposes, a human clicks "go"), confidence thresholds (auto-run when the model is sure, escalate when it isn't), and dry-run / preview mode (show what would happen before doing it). The goal isn't to slow everything down — it's to put the human exactly where their judgment is worth the interruption.

AnalogyThink of an agent like a capable new intern. You let them draft documents and run searches unsupervised (reversible, low-stakes), but you wouldn't let them wire money to a vendor without a manager signing off. You design the same checkpoints into an agentic workflow — for the same reason.
✦ Worked Example — designing a "weekly research brief" workflow

Goal: every Monday, produce a one-page brief on news in a topic you follow, grounded in real sources, and email it to yourself only after you approve it. Walk through the design decisions.

  1. Chain or loop? The number of searches isn't known in advance — some weeks have lots of news, some little. So the research step needs an agent loop (search, read, decide whether to search again). The rest (summarize → format → send) is a fixed chain. Use both: loop inside step 1, chain the remainder.
  2. Tools. Give the agent a web search tool and a fetch-page tool for the research step, and a send-email tool for delivery. Describe each clearly so the model knows when to call it.
  3. Retrieval / grounding. The summary step must cite the fetched articles. Pass the retrieved article text into the prompt (RAG) and instruct: "Summarize only from the supplied sources; mark anything you can't verify."
  4. Memory. Short-term: the list of articles found this run. Long-term: a small store of headlines already covered in past weeks, retrieved at the start so the brief doesn't repeat last week's news.
  5. Evaluation. Build a 10-example test set of past weeks with hand-written "good brief" notes. Score each generated brief with an LLM-as-judge rubric (grounded? on-topic? non-repetitive?) and spot-check a couple yourself. Track accuracy when you tweak the prompt.
  6. Human in the loop. Sending email to others would be high-impact — but here it only emails you, low-stakes and reversible. Still, put a one-click approval gate before send so a hallucinated brief never goes out unread. Searching and summarizing auto-run.
  7. Result. A workflow that is mostly autonomous, grounded in real sources, measured for quality, and gated at exactly the one step where a mistake would matter. That is a well-designed agentic workflow.

🛠️ Hands-On: prototype an agentic workflow by hand

You don't need any API keys to learn the shape of a workflow — you can role-play the loop using a free-tier chat model (Claude, ChatGPT, or Grok all have free access; tiers change, so verify current limits) and a Jupyter notebook as your scratchpad/state store. (One-line reminder: the Python + Jupyter setup is the same one-time install from Week 1 — reuse that environment.)

Part A — Run the loop manually in a free chat model. Paste this system framing, then act as the "tool" yourself by answering its tool requests:

# Paste into a free-tier chat model (Claude / ChatGPT / Grok):
You are a research agent. Goal: brief me on recent EV battery news.
Work in a loop. Each turn output EXACTLY one of:
  THINK: <your reasoning>
  ACTION: SEARCH("query")        # I will paste back fake "results"
  ACTION: FETCH("result #")      # I will paste back article text
  FINAL: <the one-paragraph brief, citing which results you used>
Do ONE step, then stop and wait for me. Start now.

Notice the model reasons, then acts (this is the ReAct pattern from Week 6), waits for an observation, and loops — exactly the agent loop, with you standing in for the tools. Try giving it a "result" that contradicts itself and watch whether it grounds the brief correctly or hallucinates.

Part B — Keep a Jupyter prompt log (your state + eval store). A notebook makes the otherwise-invisible state visible:

# agentic_log.ipynb — Lecture 7 (no API key needed)
state = {
    "goal": "EV battery news brief",
    "steps": [],          # short-term memory: the running loop log
    "covered_before": ["solid-state delays"],  # long-term memory
}

def log(turn_type, content):
    state["steps"].append({"type": turn_type, "content": content})
    print(f"[{turn_type}] {content}")

# paste each turn from the chat model as you go:
log("THINK",  "Need recent news; search broadly first.")
log("ACTION", 'SEARCH("EV battery 2026 breakthroughs")')
log("OBSERVE", "result1: ... result2: ...")   # what you pasted back
log("FINAL",  "This week: ... [used result1, result2]")

# --- tiny eval: did the FINAL stay grounded + non-repetitive? ---
final = state["steps"][-1]["content"].lower()
grounded   = "result" in final            # cited a source?
not_repeat = all(t not in final for t in state["covered_before"])
print("grounded:", grounded, "| non-repetitive:", not_repeat)

Run it for two or three topics. The log is your short-term state; covered_before is long-term memory; the last two lines are a baby eval. Add one human-in-the-loop line — input("Approve send? (y/n): ") — before any imagined "send" step to feel where a gate belongs.

🔗 Where this is heading

The pattern you built by hand — loop, tools, retrieval, memory, eval, approval gate — is exactly what production agent frameworks automate, and what the major tools now expose: standardized tool-calling interfaces, hosted retrieval, and persistent memory features. The same five pillars scale from a one-notebook prototype to systems that file expense reports or triage support tickets. Next week you'll see how Claude, ChatGPT, and Grok each package these capabilities, and how to pick the right tool for a given job — then in the Week 10 capstone you'll assemble your own personal AI operating system from these parts.

❓ Lecture 7 Quiz

7 questions · click "Show answer" to check yourself.

Q1. You know the exact steps a task needs and they're the same every time. The better structure is…
A. a fixed prompt chain
B. a full agent loop that decides each step at runtime
C. a larger model with no structure
D. retrieval-augmented generation only
Show answer

A. When the recipe is fixed, a deterministic chain is cheaper, faster, and far easier to debug. Save the dynamic agent loop for tasks whose steps depend on intermediate results.

Q2. What is the main purpose of RAG (Retrieval-Augmented Generation)?
A. to make the model train faster
B. to ground answers in supplied source text, reducing hallucination
C. to shrink the model's parameter count
D. to remove the need for any context window
Show answer

B. RAG retrieves relevant chunks and pastes them into the prompt so the model answers from grounded, often fresh, sources rather than from memory alone — which lowers hallucination and enables citations.

Q3. Across two separate API calls with no history re-sent, what does the model remember from the first call?
A. everything, models have permanent memory
B. only the last token
C. nothing — if you didn't re-send it, it's gone
D. only numbers, not text
Show answer

C. A model has no built-in cross-call memory. It only "knows" what's in the context window you send this turn. Persistent memory must live outside the model and be re-supplied.

Q4. Why is a single successful demo a poor measure of an AI workflow?
A. demos are illegal
B. models are deterministic, so one run tells you everything
C. the model can only answer once per day
D. outputs are probabilistic, so you must measure quality across many cases (an eval)
Show answer

D. The same prompt can yield different answers, so trust comes from measuring accuracy over a test set — running the eval before and after every change.

Q5. Which action most clearly belongs behind a human approval gate?
A. summarizing an article into bullet points
B. wiring money to a vendor
C. drafting a paragraph for you to read
D. running a web search
Show answer

B. Wiring money is high-impact and hard to reverse — exactly the top-right of the risk grid. The other three are reversible, low-stakes, and fine to auto-run.

Q6. In retrieval, two text chunks are judged "similar" when their embedding vectors have…
A. the same number of characters
B. high cosine similarity (point in nearly the same direction)
C. opposite directions
D. a cosine similarity of exactly 0
Show answer

B. Cosine similarity near 1 means the vectors point the same way — close in meaning. Near 0 means unrelated; the top-k highest-scoring chunks are retrieved into the prompt.

Q7. A teammate says: "Let's paste our entire 500-page archive into every prompt so the model never misses anything." The best response is…
A. agree — more context is always strictly better
B. agree — it makes the model faster
C. push back — it's slower, costlier, and can lower accuracy; retrieve only what's relevant
D. push back — context windows can't hold any documents at all
Show answer

C. Bloated context costs more and can bury key facts ("lost in the middle"), hurting accuracy. Use retrieval to bring in only the relevant chunks rather than dumping the whole archive.
