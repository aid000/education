From Chatbots to Agents

A chatbot answers your message. An agent takes your goal, makes a plan, uses tools, checks what happened, and keeps going — until the job is done or it needs you.

🎯 Learning Objectives

  • State the four ingredients that turn a chatbot into an agent: planning, tool calling, memory/state, and a loop.
  • Trace the perceive → reason → act → observe cycle that an agent repeats toward a goal.
  • Describe the ReAct pattern — interleaving a written "thought" with an "action" and an "observation."
  • Reason about the autonomy-vs-control trade-off and why errors can compound over multi-step runs.
  • Decide where a human-in-the-loop checkpoint belongs and why verification is non-negotiable.

6.1Chatbot vs. Agent — the Real Difference

You have spent two weeks (Weeks 4–5) learning to prompt: shape one request, get one good answer back. That is a chatbot interaction — it is turn-based. You speak, the model speaks, and nothing happens in the world between turns. The model has no hands and no clock; it only emits text.

An agent is the same underlying model placed inside a program that gives it three new powers: the ability to act on the world through tools, the ability to remember what it has done, and a loop that lets it keep going without waiting for you at every step. The model still only outputs text — but now some of that text is interpreted as a command to run a tool, and the result is fed back in.

chatbot:  you → model → answer   (stop)
agent:    goal → [ plan → act via tool → observe ] ↺ → resultThe brackets repeat. The agent decides when to stop — that is the part that earns the word "autonomy."

So the dividing line is not intelligence — it is the same model. The line is the loop plus the tools plus the memory. Take any of those away and you are back to a chatbot that happens to be very capable.

AnalogyA chatbot is a brilliant friend on the phone: ask anything, get great advice, hang up. An agent is that same friend given your house keys, a to-do list, and a car — now they can actually go buy the groceries, notice the store was out of milk, drive to a second store, and text you only when they hit a real decision. The brain is identical; what changed is that they can act, remember, and keep going.

6.2The Four Ingredients

Strip an agent down and you always find the same four parts working together. Lose one and the whole thing degrades.

1 · Planning

Given a goal ("book me a quiet table for four on Friday"), the agent first decomposes it into steps — the exact skill from Week 5, now done by the model itself. A plan can be written up front or formed one step at a time as new information arrives.

2 · Tool calling

A tool is any function the agent is allowed to invoke: a web search, a calculator, code execution, a database query, a calendar API. The model emits a structured request like search("quiet restaurants near me"); the surrounding program actually runs it and returns the result as text. Tools are what let a text-only model touch the real world.

3 · Memory / state

The agent must remember the goal, the steps already taken, and what each tool returned — otherwise it loops forever or repeats itself. Short-term memory lives in the context window; longer-term memory is often stored outside and retrieved when relevant (a theme we deepen in Week 7).

4 · The loop

A controller repeatedly asks the model "what next?", runs the chosen action, feeds the observation back, and checks whether the goal is met. This perceive → reason → act → observe cycle is the engine of every agent.

6.3The ReAct Pattern — Reason + Act

How do we get a next-token predictor to use tools sensibly instead of just describing them? The most influential answer is the ReAct pattern (short for Reason + Act, a research framing from around 2022–2023 — treat it as a durable pattern, not a fixed product feature). The idea is simple: make the model interleave thinking out loud with taking actions, in a fixed three-part rhythm.

Thought → Action → Observation  (repeat)The model writes its reasoning, emits one tool call, then reads the result before thinking again.

A run looks like a transcript the model both writes and reads:

# Goal: "What's the population of the capital of Australia?"
Thought: I'm not certain of Australia's capital. I should look it up.
Action: search("capital of Australia")
Observation: The capital of Australia is Canberra.
Thought: Now I need Canberra's population.
Action: search("population of Canberra")
Observation: Canberra's population is approximately 460,000.
Thought: I have the answer.
Answer: The capital is Canberra, with roughly 460,000 people.

Why interleave instead of planning everything first? Because the world talks back. The observation after each action carries information the model could not have known in advance (the store is out of milk; the search returned nothing; the code threw an error). Writing a fresh Thought after each Observation lets the agent adapt — this is chain-of-thought reasoning fused with the ability to act and re-plan.

AnalogyReAct is cooking from a recipe while actually tasting the dish. A pure-planning agent writes the whole recipe, then executes it blind, even if step 2 already came out too salty. A ReAct agent tastes after every step (the Observation), thinks "too salty — skip the added salt" (the next Thought), and adjusts the rest. Acting and reasoning take turns, so reality keeps steering the plan.

6.4Autonomy vs. Control & Why Errors Compound

Every agent sits somewhere on a dial. Turn it one way and the agent asks you to approve each step (high control, low autonomy); turn it the other way and it runs the whole task unsupervised (high autonomy, low control). Neither extreme is "right" — the correct setting depends on how reversible and how costly a mistake is.

The reason this dial matters is error compounding. Suppose each step in a plan is 90% reliable — quite good. The chance that a whole chain succeeds is roughly the product of the per-step reliabilities:

P(run succeeds) ≈ pn  →  0.905 ≈ 0.59,  0.9010 ≈ 0.35Independent-step approximation: a 90%-reliable step, run 10 times, lands near a coin flip. Real runs aren't fully independent, but the lesson holds: length is risk.

So a longer autonomous run is not just "more work" — it is geometrically more likely to drift off course, and an early wrong turn (a misread instruction, a bad search result accepted as truth) can be quietly carried through every later step. The longer the leash, the more a small early error can snowball.

Common mistakeDon't assume "the agent looped, so it must have converged on the right answer." A loop can confidently run to completion while having gone wrong at step 2 — every later step just builds on the bad foundation. Finishing is not the same as succeeding. Give an agent the autonomy that matches the cost of being wrong: low stakes and reversible → long leash; spending money, sending email, deleting files → short leash with approval.

6.5Keeping a Human in the Loop

The fix for error compounding is not "make the model perfect" — it is to insert verification at the right places. A human-in-the-loop (HITL) design keeps a person at the decision points that matter, while letting the agent grind through the safe, repetitive parts on its own. You are not babysitting every token; you are guarding the irreversible moves.

Three durable rules for where the human belongs:

  • Gate the irreversible. Sending an email, charging a card, deleting data, publishing — require an explicit human "yes" before the agent does any of these.
  • Verify the load-bearing. Numbers, citations, code that will run, claims you'll act on — check these against a real source (an echo of Week 5's "self-critique is not a fact-checker").
  • Checkpoint long runs. Have the agent pause and summarize its plan/progress at milestones, so an early wrong turn is caught before it compounds.

Notice the symmetry: the more autonomy you grant, the more these checkpoints earn their keep. A well-designed agent is not the one that needs you least — it is the one that knows when to stop and ask.

AnalogyA human-in-the-loop agent is a self-driving car with a steering wheel. It handles the boring highway miles on its own, but it hands control back — or simply stops and asks — at the ambiguous, high-stakes moments (a closed road, an unusual intersection). The autonomy is real; the human stays where a mistake would be expensive to undo.
✦ Worked Example — designing an agent to "tidy my inbox and reply to the easy ones"

Goal: an agent triages today's email. Watch how the four ingredients, the ReAct rhythm, and the human checkpoints fall into place.

  1. Name the goal & plan (decompose): read inbox → classify each message (urgent / reply-now / archive / needs-me) → draft replies for the easy ones → present a summary for approval.
  2. Pick the tools: list_emails(), read_email(id), draft_reply(id, text). Critically, give it draft_reply, not send_email — drafting is reversible, sending is not.
  3. One ReAct turn: Thought: "Message 4 is a meeting reschedule — I can reply." → Action: draft_reply(4, "Tuesday works…") → Observation: "draft saved." → next Thought.
  4. Memory keeps it honest: the agent records which IDs it has already handled, so the loop doesn't re-process message 4 or run forever.
  5. Set the autonomy dial: classifying and drafting are reversible → full autonomy. Sending anything → stop and require a human "yes."
  6. Insert the human-in-the-loop checkpoint: the agent ends with "Here are 6 drafts and 3 messages flagged for you. Approve which to send?" You verify the load-bearing replies and click send yourself.
  7. Takeaway: the agent did the tedious 90% autonomously, but the one irreversible action (send) was gated behind a human. Error compounding is contained because the only step that touches the outside world waits for you.

Use any free-tier chat assistant (Claude, ChatGPT, or Grok all work). One-line reminder: the Python/Jupyter setup from Week 1 is all you need for the log step — no new installs.

Exercise — make a plain chatbot act like an agent by hand:

# 1. FORCE THE ReAct RHYTHM — paste this, then a small goal
Act as a ReAct agent. For my goal, respond ONLY in this loop:
  Thought: (your reasoning)
  Action: (one tool from: search[q], calc[expr], ask_human[q])
Then STOP and wait. I will play the tools and paste back:
  Observation: (result)
Continue until you can give a final Answer.
Goal: plan a 3-stop walking route between three places I name.

# 2. YOU ARE THE TOOLS — answer each Action with an Observation,
#    and notice every time it (correctly) emits ask_human[...]

# 3. STRESS-TEST AUTONOMY — give a SECOND Observation that's wrong
#    ("that street is closed") and watch whether it re-plans (good ReAct)
#    or barrels ahead on the stale plan (error compounding).

Run the same goal in two different assistants and note which one pauses to ask_human at the right moment.

Q1. What is the core difference between a chatbot and an agent?
A. An agent uses a fundamentally smarter, larger model
B. An agent runs a loop that lets it plan, use tools, keep memory, and act toward a goal
C. A chatbot can't answer questions
D. An agent never uses text
Show answer

B. It can be the very same model. The difference is the loop + tools + memory wrapped around it — not raw intelligence.

Q2. Which is not one of the four ingredients of an agent?
A. Planning
B. Tool calling
C. A larger context window than any chatbot
D. Memory / state
Show answer

C. The four are planning, tool calling, memory/state, and the loop. A big context window can help, but it isn't what defines an agent.

Q3. In the ReAct pattern, the repeating rhythm is…
A. Thought → Action → Observation, repeated
B. Plan the entire run first, then execute it blindly
C. Answer immediately with no reasoning
D. Call every available tool at once
Show answer

A. The model writes its reasoning, emits one action, reads the observation, then thinks again — interleaving reasoning with acting so reality can steer the plan.

Q4. Why interleave reasoning and acting (ReAct) instead of planning everything up front?
A. It uses fewer tokens
B. It removes the need for tools
C. Each observation carries new information, so the agent can adapt and re-plan
D. It guarantees the answer is correct
Show answer

C. The world talks back — a tool result the model couldn't predict (an error, an empty search, a closed road) lets it course-correct on the next Thought.

Q5. If each step in a plan is 90% reliable, the chance a 10-step autonomous run fully succeeds is closest to…
A. 99%
B. 90%
C. 75%
D. about 35% (errors compound: 0.9¹⁰ ≈ 0.35)
Show answer

D. Roughly pn = 0.9¹⁰ ≈ 0.35. Even reliable steps multiply into real risk over a long run — length is risk.

Q6. An agent finished its loop and produced a result. What should you conclude?
A. Finishing the loop proves the answer is correct
B. Finishing is not the same as succeeding — it may have gone wrong early and built on it
C. The longer it ran, the more trustworthy the result
D. No verification is needed once it stops
Show answer

B. A loop can confidently run to completion on a bad step-2 foundation. Always verify load-bearing output regardless of how cleanly it finished.

Q7. Where does a human-in-the-loop checkpoint belong first?
A. On every single token the agent produces
B. Nowhere — autonomy means no human
C. Before irreversible or high-cost actions (send, pay, delete, publish)
D. Only after the task is completely finished
Show answer

C. Gate the irreversible, verify the load-bearing, and checkpoint long runs. You guard the costly, undo-resistant moves — not every routine step.
