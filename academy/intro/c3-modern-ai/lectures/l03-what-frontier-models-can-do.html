Week 3 · Lecture 3

What Frontier Models Can Do

Today's best models see, hear, write code, reason through problems, and reach out to tools — but each capability comes with a sharp edge. Here is the honest map.

🎯 Learning Objectives

  • Describe what multimodality means and which modalities (text, image, code, audio) frontier models commonly handle.
  • Explain how a reasoning model differs from a plain chat model and when "thinking longer" actually helps.
  • Define tool use / function calling and trace how a model decides to call a tool and use its result.
  • Explain what a model's context window is, why long context matters, and where it still fails.
  • Match a real task to the capability it needs — and name where today's models are still weak.

3.1One Model, Many Modalities

In Weeks 1–2 you saw that a model is fundamentally a next-token predictor trained on huge amounts of data. The surprising part: if you turn images, audio, and code into tokens too, the same architecture can learn all of them. A multimodal model accepts more than one kind of input — typically text and images, and increasingly audio — and produces text (and, in some systems, images or speech) as output.

The trick is that everything becomes a sequence of vectors (embeddings) the Transformer can attend over. A patch of an image, a slice of audio, or a word are each mapped into the same kind of numeric token, so the model reasons over them together.

AnalogyThink of tokens as a common currency. A traveler arriving with dollars, euros, and yen can't spend them side by side — but converted to one currency, they all add up in the same wallet. Multimodal models convert pictures, sound, and words into one "currency" (embeddings) so a single brain can spend them together.

Code is a special, important case of text: because programming languages are highly structured and abundant on the web, models become unusually strong at reading, writing, and explaining code. That strength is the foundation for tool use in §3.3.

3.2Reasoning Models — Thinking Before Answering

A plain chat model emits its answer token-by-token, left to right, with no scratch paper. That works for recall and fluent writing but stumbles on multi-step problems (long arithmetic, logic puzzles, careful planning). A reasoning model is trained to first generate a private chain of intermediate steps — a "thinking" phase — before committing to a final answer.

more "thinking" tokens ⟶ more steps of self-conditioning ⟶ better multi-step answersSpending extra computation at answer-time ("test-time compute") often raises accuracy on hard, multi-step problems — up to a point.

This is the same idea as chain-of-thought (you'll prompt for it by hand next week) — but baked into the model through training so it happens automatically. The cost: reasoning models are usually slower and more expensive per answer, because they generate many hidden tokens you never see.

Common mistake"Reasoning" does not mean the model is correct, only that it works step by step. A longer chain of thought can still be confidently wrong, and the visible "thinking" is a generated narrative, not a guaranteed audit trail of the real computation. For simple lookups or quick drafts, a reasoning model is often slower for no benefit — match the tool to the task.

When to reach for a reasoning model

Use it for math, code debugging, planning, and "show your work" problems. Skip it for casual chat, quick rewrites, or brainstorming where speed matters more than rigor.

3.3Tool Use & Function Calling

A model alone is frozen in its training data and can't do anything in the world — it only emits text. Tool use (a.k.a. function calling) breaks that wall: you describe a set of functions the model may call (a calculator, a web search, a database query, a code runner), and the model can choose to emit a structured request to use one. Your program runs the tool and feeds the result back, then the model continues.

Function calling works because models are good at producing structured output (e.g. JSON) — "name the function and its arguments." This single mechanism powers calculators that fix arithmetic, live web search that fixes stale knowledge, and code execution that fixes guessing. It is the bridge from a chatbot that talks to an agent that acts.

3.4Long Context — How Much It Can Hold at Once

Everything the model can "see" for a single response — your prompt, the conversation so far, any documents you paste, tool results — must fit inside its context window, measured in tokens. Early models held a few thousand tokens (a handful of pages). Frontier models now advertise context windows of hundreds of thousands of tokens (specific limits vary by model and change often — as of 2026, verify against current official sources), enough for whole books or large codebases.

≈ 1 token ≈ ¾ of an English word → 100K tokens ≈ ~75,000 words ≈ a short novelA rough rule of thumb for English; actual ratios depend on the tokenizer and language.

Long context unlocks "read this whole report and answer questions," "refactor across these 30 files," and "remember our 2-hour conversation." But two cautions matter:

  • "Lost in the middle." Models tend to use information at the very start and very end of a long context more reliably than facts buried in the middle. Put the most important material near the edges.
  • Big window ≠ free or instant. Cost and latency typically grow with how much context you feed in, and the window is a hard ceiling — overflow it and the oldest content silently drops.
Note · context is not memoryA model does not "remember" past chats unless that text is placed back into the context window each turn. Persistent memory is a feature your app builds on top — not something the raw model has. We return to this when we build agents.

3.5Strong Where, Weak Where

Put the four capabilities together and a pattern emerges. Frontier models are strong at fluent language, pattern completion, code, summarizing and transforming text you give them, and multi-step reasoning on well-specified problems. They are weak at knowing what they don't know — they will produce a confident, fluent answer even when it is fabricated (a hallucination, covered fully in Week 9).

The honest summary: today's models are excellent transformers of information you supply and generators of plausible drafts, and increasingly capable reasoners and tool-users — but they are not reliable sources of truth on their own. The capabilities in this lecture (especially tool use and long context) exist largely to compensate for that weakness: give the model the real document, let it search, let it run the code, and check the result.

✦ Worked Example — picking the right capability for the job

You receive four tasks. For each, decide which capability it needs and whether a plain chat model suffices.

  1. "Read this 60-page contract PDF and list every deadline." → Needs long context (paste the whole document) and ideally multimodality if it's a scanned image. Plain chat is fine if the text fits the window; put your real question at the end.
  2. "What is 48,271 × 9,338, exactly?" → A model guessing token-by-token will likely be off. Needs tool use (a calculator/code tool) — or expect errors. This is a classic case where capability, not cleverness, is the fix.
  3. "Plan a 5-step migration of our database with rollback at each step." → A multi-step planning problem: reach for a reasoning model so it works through dependencies before answering.
  4. "Describe what's happening in this photo of a circuit board." → Needs multimodality (image input). A text-only model literally cannot see it.
  5. Takeaway: the skill is not "use AI" but "name the capability the task demands," then pick a model/mode that has it — and verify anything factual.

🛠️ Hands-On: probe the four capabilities yourself

Use any free-tier chat model (the Week 1 setup still applies — no new install needed). Run these four mini-tests and log what you observe in a Jupyter notebook so you can compare models later.

Try in the chat UI:

  • Multimodal: upload a photo of a handwritten note and ask the model to transcribe it.
  • Reasoning: ask a logic puzzle twice — once normally, once with a "reasoning"/"think step by step" mode — and compare.
  • Tool use: ask "what is 48271 × 9338?" then ask it to "use a calculator or run code to verify." Note any difference.
  • Long context: paste a long article and ask a question about one sentence hidden in the middle.

Then keep a structured prompt log in Jupyter so your experiments are reproducible:

# capability_log.ipynb — Week 3
log = []

# record one experiment per capability you test
log.append({
    "capability": "tool_use",
    "model": "(which model / mode you used)",
    "prompt": "What is 48271 * 9338? Use a calculator to verify.",
    "expected": 450755398,                 # the true product
    "got": "...",                          # paste the model's answer
    "correct": None,                       # fill True/False after checking
    "notes": "did it call a tool or just guess?"
})

for e in log:
    flag = "?" if e["correct"] is None else ("OK" if e["correct"] else "WRONG")
    print(f'[{flag}] {e["capability"]:9} | {e["model"]}')
# 48271 * 9338 == 450,755,398 — confirm with Python: print(48271 * 9338)

The point of the log is honesty: write down when the model was wrong, not just when it impressed you. That record is the raw material for this week's discussion below.

🔗 Where this is heading

Each capability here becomes a building block in the weeks ahead. Long context plus structured output is what lets you give an agent a big task brief (Weeks 6–7). Tool use is the literal mechanism behind agents that browse, run code, and edit files. Reasoning is what you'll soon trigger by hand with chain-of-thought and tree-of-thoughts (Weeks 4–5). By the capstone you'll wire several of these together into a personal "AI operating system" — but only after Week 9 teaches you exactly where the cracks are.

Q1. A "multimodal" model is one that can…
A. run on multiple operating systems
B. accept more than one kind of input, such as text and images
C. be trained by multiple companies at once
D. only output in one language
Show answer

B. Multimodal = handles multiple input modalities (commonly text + images, increasingly audio), all encoded into one shared token space.

Q2. How does a reasoning model mainly differ from a plain chat model?
A. It is always factually correct
B. It never uses tokens
C. It generates intermediate "thinking" steps before its final answer
D. It only works on images
Show answer

C. It spends extra test-time compute working step by step before answering. That often helps on multi-step problems — but does not guarantee correctness (A is wrong).

Q3. In tool use / function calling, who actually runs the tool?
A. Your program runs it; the model only requests the call and receives the result
B. The model executes the code internally with no outside help
C. The user must run it by hand every time
D. Tools cannot return results to the model
Show answer

A. The model emits a structured request (function + arguments); your code runs the tool and feeds the result back so the model can continue.

Q4. A model's "context window" is…
A. the size of its training dataset
B. the maximum number of tokens it can consider for a single response
C. the number of users it can serve
D. permanent memory of every past conversation
Show answer

B. It's the token budget for one response (prompt + history + documents + tool results). It is not permanent memory (D) — text must be re-supplied each turn.

Q5. For the task "compute 48,271 × 9,338 exactly," the most reliable approach is…
A. trust the model's first token-by-token guess
B. use a longer context window
C. upload an image of the numbers
D. have the model use a calculator/code tool and verify
Show answer

D. Exact arithmetic is a weak spot for raw next-token prediction; tool use (a calculator or code) is the dependable fix. The true product is 450,755,398.

Q6. The "lost in the middle" effect means that in a long context, models tend to…
A. use information at the start and end more reliably than facts buried in the middle
B. forget the first and last tokens
C. ignore all images
D. double the cost of every request
Show answer

A. Recall is typically strongest at the edges of a long context and weaker for middle content — so place key material near the start or end.

✓ What you learned

  • Multimodality: text, images, audio (and code) are all turned into tokens so one model can reason across them.
  • Reasoning models generate intermediate steps before answering — helpful on multi-step problems, but not a guarantee of correctness.
  • Tool use / function calling: the model requests a structured call, your code runs it, and the result comes back — the bridge from chatbot to agent.
  • Long context is a per-response token budget; it enables whole-document work but suffers "lost in the middle" and is not permanent memory.
  • Match the capability to the task, and remember models are confident even when wrong — verify anything factual.
