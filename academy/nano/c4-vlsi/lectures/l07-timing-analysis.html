Week 7 · Lecture 7

Static Timing Analysis

Proving a design meets timing on every path — without simulating a single test vector.

🎯 Learning Objectives

  • Explain why static timing analysis (STA) verifies every path exhaustively, with no test vectors.
  • Distinguish a setup check (path too slow) from a hold check (path too fast).
  • Define slack = required time − arrival time, and identify positive vs. negative slack.
  • Identify the critical path as the path with the least (most negative) slack.
  • Choose the right fix: faster cells / less logic depth / pipelining for setup; added buffers for hold.

7.1Why STA?

Once a netlist is synthesized, you need to prove it runs at the target clock frequency. Functional simulation can tell you the logic is correct, but it only checks the cases you bother to exercise — a handful of test vectors out of an astronomical number of possible input patterns. A timing bug on an un-exercised path slips right through.

Static timing analysis (STA) takes the opposite approach. It is static — it never runs the circuit. Instead it walks the netlist's delay graph and verifies, mathematically and exhaustively, that the timing on every path meets the clock's requirements.

STA checks all paths · no test vectors · no simulationSimulation checks the cases you exercise; STA proves timing on every path at once.

Because it considers all paths in one analysis, STA is the standard sign-off check for whether a design "makes timing." If STA passes, you are guaranteed no path violates the clock — for any input pattern.

7.2Setup & Hold Checks

Every timing path runs from a launching flip-flop, through some combinational logic, to a capturing flip-flop. Both flops are clocked. For the captured value to be correct, the data must be stable in a window around the capturing clock edge. STA enforces this with two checks:

Setup check — is the path too slow?

The data launched on one clock edge must arrive and settle before the next capturing edge's deadline. A setup violation means data arrives too late — the path is too SLOW.

Hold check — is the path too fast?

The data must also hold steady just after the capturing edge, so the new value doesn't race through and corrupt what's being latched. A hold violation means data changes too soon after the edge — the path is too FAST.

setup fails ⟹ path too SLOW  ·  hold fails ⟹ path too FAST
AnalogySTA is like checking that every runner in a relay finishes before the baton handoff — the clock edge. You don't stand and watch one race (that's a single simulation run, one set of inputs); you mathematically verify every possible path's timing at once. A runner who's too slow misses the handoff (setup); a runner who hands off too early, before the next runner is ready, fumbles the baton (hold).

7.3Slack: the Timing Margin

STA quantifies how comfortably a path meets timing with a single number, slack. For each endpoint it computes when the signal is required to be there and when it actually arrives, then subtracts:

slack = required time − arrival timePositive slack ⟹ meets timing. Negative slack ⟹ a violation.

A positive slack means the data shows up with margin to spare — the path passes. A negative slack means it shows up after its deadline — the path fails. The amount of negative slack tells you how badly, and by how much you have to speed the path up.

Among all the paths in a design, the one with the least (most negative) slack is the critical path. It is the bottleneck that sets the maximum clock frequency: improve it and the whole design can run faster.

7.4Fixing Timing Violations

The fix depends on which check failed — and these pull in opposite directions, so you must diagnose first.

Setup violations (path too slow) — speed it up

You need the data to arrive sooner. Options:

faster cells · less logic depth · pipelining

Swap in higher-drive or low-threshold standard cells, restructure the logic to reduce the number of stages between flops, or insert a pipeline register to split a long combinational path into two shorter ones.

Hold violations (path too fast) — slow it down

You need the data to arrive a little later, so it stays stable past the capturing edge. The fix is to add delay:

insert buffers (delay) on the too-fast path

Adding buffer cells lengthens the short path just enough to satisfy the hold requirement, without disturbing the (already-met) setup margin.

Common mistakeDon't confuse the two checks. A SETUP violation means the path is too SLOW — speed it up (faster cells, less logic, pipelining). A HOLD violation means the path is too FAST — add delay (buffers). Remember too that STA is exhaustive and static: it needs no test vectors and runs no simulation, yet covers every path. And negative slack means timing FAILS — positive slack is the passing case.
✦ Worked Example — Computing Slack

A path is clocked with a period of 2 ns, and the capturing flop has a setup time of 0.2 ns. Find the required time, then the slack for two cases: (a) arrival time 1.6 ns, and (b) arrival time 2.0 ns.

  1. Required time: required = period − setup = 2 − 0.2 = 1.8 ns (the deadline for data to arrive).
  2. Case (a), arrival = 1.6 ns: slack = required − arrival = 1.8 − 1.6 = +0.2 ns → positive slack, the path MEETS timing.
  3. Case (b), arrival = 2.0 ns: slack = 1.8 − 2.0 = −0.2 ns → negative slack, a SETUP VIOLATION — the path is too slow.
  4. Fix for (b): speed the path up (faster cells, less logic depth, or pipelining) to pull arrival back under 1.8 ns.

🛠️ Hands-On: run STA and read the worst-slack report

OpenLane runs OpenSTA as its sign-off timing engine. After synthesis (or any stage), pull up the timing report and find the worst negative slack and the critical path. You can also drive OpenSTA standalone on a netlist + Liberty + SDC.

# In an OpenSTA / OpenROAD shell, after reading the design:
read_liberty sky130.lib
read_verilog design.synth.v
link_design top
read_sdc design.sdc

# worst setup slack + the offending critical path
report_checks -path_delay max -slack_max 0 -fields {slack}

# worst hold slack
report_checks -path_delay min

Read off the slack at the bottom of each path report: a negative value flags a violation. Then compute slack by hand for one path — required = clock period − setup time, slack = required − arrival — and confirm it matches the tool. Predict whether tightening the clock period will create new violations before you re-run.

❓ Lecture 7 Quiz

5 questions · click "Show answer" to check yourself.

Q1. Static timing analysis…
A. simulates a few representative test cases
B. checks timing on all paths exhaustively, without test vectors
C. measures the dynamic power of the design
D. runs only once, at tape-out
Show answer

B. STA is static and exhaustive — it walks the delay graph and verifies every path, needing no test vectors and no simulation. Simulation only checks the cases you exercise.

Q2. A setup violation means the path is…
A. too slow (data arrives after the deadline)
B. too fast
C. unconnected
D. asynchronous
Show answer

A. Setup fails when data arrives after the capturing edge's deadline — the path is too slow. Fix it by speeding it up (faster cells, less logic, pipelining).

Q3. Slack is defined as…
A. arrival time minus required time
B. required time minus arrival time (positive = meets timing)
C. the clock period
D. the gate count of the path
Show answer

B. slack = required − arrival. Positive slack means the data arrives with margin (meets timing); negative slack is a violation.

Q4. The critical path is the path with…
A. the most gates, always
B. the least (most negative) slack
C. the highest power
D. the longest wire only
Show answer

B. The critical path has the least (most negative) slack — it's the bottleneck that sets the maximum clock frequency. Not necessarily the most gates or the longest wire.

Q5. A hold violation is fixed by…
A. using faster cells
B. raising the clock frequency
C. adding delay (buffers) on the too-fast path
D. removing a flip-flop
Show answer

C. A hold violation means data arrives too fast, so you add delay (buffers) to the short path to keep it stable past the capturing edge. Faster cells would make it worse.

✓ What you learned

  • STA verifies timing on every path exhaustively, statically and with no test vectors — unlike simulation, which checks only the cases you exercise.
  • A setup check fails if a path is too slow; a hold check fails if a path is too fast.
  • slack = required − arrival; positive meets timing, negative is a violation.
  • The critical path has the least (most negative) slack and sets the max clock frequency.
  • Fix setup with faster cells / less logic depth / pipelining; fix hold by adding buffer delay.
