Hardware Description Languages (Verilog)

Describing hardware that all runs at once — not writing a sequential program.

🎯 Learning Objectives

  • Explain why Verilog describes hardware running in parallel rather than executing as a sequential program.
  • Define a module with input/output ports, and distinguish wire from reg.
  • Use assign / always @(*) for combinational logic and always @(posedge clk) for sequential logic.
  • Apply the blocking = vs nonblocking <= rule correctly.
  • Simulate a design with a testbench and read its waveforms — and tell simulation apart from synthesis.

3.1Describing Hardware, Not Programming

The hardest mental shift in Verilog is this: you are not writing a program that runs line by line. You are describing hardware — a network of gates, wires, and registers whose parts all operate at the same instant, all the time. The text of your file is a description of structure and behavior; the synthesized circuit has no notion of "the line above runs first."

A software function executes one statement, then the next. A Verilog design is more like a wiring diagram: every assign and every always block is a separate piece of hardware that exists simultaneously and reacts continuously to its inputs. Internalize this and most Verilog confusion disappears.

3.2Modules, Ports & Signals

The basic unit is the module — a self-contained hardware block with input and output ports, like a chip on a schematic. You wire modules together by connecting their ports; larger designs are hierarchies of smaller modules.

Inside a module, two signal types matter most. A wire carries a combinational signal — it must be continuously driven (by an assign or a module output) and simply reflects whatever drives it. A reg holds a value assigned inside a procedural block (always/initial); despite its name it does not always become a hardware register — it becomes one only when a clocked block infers storage.

3.3Combinational vs Sequential Constructs

Verilog gives you two families of constructs, and each maps to a different kind of hardware.

Combinational

A continuous assign, or an always @(*) block, describes combinational logic — outputs that are a pure function of the current inputs, with no memory. Inside combinational blocks, use the blocking assignment =.

Sequential

An always @(posedge clk) block describes logic that updates on a clock edge, which the tool implements with flip-flops — it infers storage. Inside clocked blocks, use the nonblocking assignment <= so that all registers sample their inputs together, matching real edge-triggered hardware.

assign / always @(*) → combinational  ·  always @(posedge clk) → sequential (flip-flops)blocking = in combinational blocks · nonblocking <= in clocked blocks

3.4Simulation & Testbenches

You verify a design before building it. A testbench is itself Verilog: it instantiates your module, drives its inputs over time, and lets you observe the outputs. Free tools make this easy — compile and run with Icarus Verilog (iverilog) or Verilator, dump signals to a file, and view the waveforms in GTKWave.

One caution: simulation ≠ synthesis. A testbench freely uses constructs that have no hardware meaning — #10 delays, $display, initial blocks, large unbounded loops. These run fine in a simulator but a synthesis tool will reject or ignore them. The synthesizable subset is smaller than the full language.

AnalogyWriting Verilog is like drawing a wiring diagram, not writing a recipe. A recipe is steps you follow in order. A wiring diagram shows components that all exist and operate at the same time. Every always block and every assign is a piece of hardware that is "always on" — not a step that runs only after the line above it finishes.
Common mistakeVerilog is parallel hardware, not sequential code. All blocks run concurrently, and the textual order of blocks does not imply an order in time. Use nonblocking <= in clocked blocks and blocking = in combinational ones — mixing them causes simulation/hardware mismatches, races, or unintended latches. And remember not all Verilog is synthesizable: sim-only constructs describe no gates.
✦ Worked Example

Same language, two snippets — each describes a different piece of hardware, and both can coexist in one design, operating at the same time.

  1. Combinational: assign y = sel ? b : a; describes a 2:1 multiplexer — y continuously follows a or b depending on sel, with no clock and no memory.
  2. Sequential: always @(posedge clk) q <= d; infers an edge-triggered D flip-flop — on each rising clock edge, q captures the value of d and holds it until the next edge.
  3. Takeaway: identical syntax style, completely different hardware. The mux is pure logic; the flop is storage. Put both in a module and they run concurrently, not one-after-another.

🛠️ Hands-On: simulate a mux and view the waveform

Write a small module plus a testbench, simulate with Icarus Verilog, and inspect the result in GTKWave.

// mux2.v — 2:1 multiplexer (combinational)
module mux2(input a, input b, input sel, output y);
    assign y = sel ? b : a;
endmodule

// tb_mux2.v — testbench (sim-only constructs)
module tb_mux2;
    reg a, b, sel; wire y;
    mux2 dut(a, b, sel, y);
    initial begin
        $dumpfile("mux2.vcd"); $dumpvars(0, tb_mux2);
        a=0; b=1; sel=0; #10
        sel=1;            #10
        a=1; b=0;         #10
        $finish;
    end
endmodule

Build and run: iverilog -o mux2 mux2.v tb_mux2.v then vvp mux2. Open the waveform with gtkwave mux2.vcd and confirm y follows a when sel=0 and b when sel=1. Note the #10 delays and $dumpvars are simulation-only — they describe no hardware.

Model response

Every assign and always block becomes physical hardware that operates simultaneously; the textual order of blocks does not imply an order in time. If you think of Verilog as sequential code you expect lines to "run" one after another, which isn't how the synthesized circuit behaves — the gates and registers are all there at once, reacting continuously.

Typical bugs from a software mindset: mixing blocking and nonblocking assignments so simulation and hardware disagree or a race appears; forgetting a branch in a combinational block so the tool infers an unintended latch; writing loops or big sequential state as if it were iterative software; and using non-synthesizable constructs that simulate but produce no hardware. The right mindset is to think in clock cycles, registers, and concurrent logic — describe the hardware you want, then check that it synthesizes.
