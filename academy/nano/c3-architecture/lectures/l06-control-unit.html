Control Unit

The conductor that decodes instructions and tells the datapath what to do, and when.

🎯 Learning Objectives

  • State the control unit's job: decode the current instruction and generate the signals that steer the datapath.
  • Define a finite state machine as a set of states plus the transitions between them.
  • Describe how control marches through fetch → decode → execute states each cycle.
  • Contrast hardwired control (fast, rigid) with microcoded control (flexible, slower).
  • Explain why CISC machines favored microcode while modern RISC pipelines lean hardwired.

6.1The Control Unit's Job

The datapath — registers, ALU, muxes, and memory ports from Lecture 5 — can do everything a processor needs, but it has no idea what to do on any given cycle. That's the control unit's job: take the current instruction, decode it, and generate the control signals that steer the datapath.

Those signals are exactly the knobs the datapath exposes: mux selects (which operand or write-back source to route), the ALU operation (add, subtract, AND, …), register-write enables (whether and which register latches a result), and memory read/write lines. The control unit reads the opcode and asserts the right combination so the right thing happens this cycle.

6.2Finite State Machines

One instruction usually takes several steps, so control doesn't fire all its signals at once — it marches through states. The natural model is a finite state machine (FSM): a finite set of states plus the transitions between them. Each clock edge moves the machine from one state to the next.

For a simple processor the states are the classic fetch (read the next instruction), decode (figure out what it is and read operands), and execute (do the work and write back) — then loop back to fetch. In each state the control unit asserts exactly the signals that step needs.

6.3Hardwired Control

In hardwired control, the decode-and-sequence logic is built directly out of gates — an FSM implemented as combinational logic plus a state register. The opcode and current state feed a fixed network of AND/OR gates that produces the control signals.

The payoff is speed: signals come straight out of a shallow logic network with no extra lookup, so hardwired control is compact and fast. The cost is rigidity — every instruction is baked into the gates, so changing or fixing the instruction set means redesigning the logic. This style is typical of RISC machines, whose small, regular instruction sets map cleanly onto fast hardwired control.

6.4Microcoded Control

In microcoded control, each machine instruction is implemented by a tiny microprogram — a short sequence of microinstructions stored in a control ROM. The opcode indexes into the ROM, and each microinstruction's bits are the control signals for one step.

Because behavior lives in ROM rather than in gates, microcode is flexible: adding a complex or variable-length instruction — or fixing a bug — is just editing the microcode, not respinning logic. The cost is the extra ROM lookup each step, which makes microcode slower. This style is typical of older CISC machines with rich, irregular instruction sets.

AnalogyThe control unit is the conductor of an orchestra — it doesn't play the notes (the datapath does that), it signals who plays when. Hardwired control is a fixed score engraved once and never changed; microcode is a programmable score the conductor looks up in a book, page by page — easy to revise, but it takes a moment to turn each page.
Common mistakeHardwired control is faster but inflexible; microcode trades speed for flexibility (and makes complex instructions easier to implement) — don't swap those around. And remember the control unit only generates signals; it does not compute data. The arithmetic happens in the ALU/datapath, not the control unit.
✦ Worked Example

Same datapath, two instructions — watch how only the control signals change.

  1. ADD R3, R1, R2: register-read R1 and R2, set ALU op = add, route the ALU result to write-back, register-write enabled (into R3), and memory stays idle (no read or write).
  2. LOAD R3, [R1]: the ALU computes the address from R1, memory-read enabled, the write-back mux selects memory (not the ALU result) as the source, and register-write enabled (into R3).
  3. Takeaway: the wires, ALU, and register file are identical in both cases. Only the control unit's signal pattern differs — that pattern is the difference between an add and a load.

🛠️ Hands-On: a 3-state control FSM in Verilog

Code the fetch/decode/execute FSM as a clocked always @(posedge clk) block with a case over the state. Simulate with Icarus Verilog and view the waveform in GTKWave.

// control_fsm.v — fetch/decode/execute
module control_fsm(input clk, input rst, output reg [1:0] state);
  localparam FETCH=2'd0, DECODE=2'd1, EXECUTE=2'd2;
  always @(posedge clk) begin
    if (rst) state <= FETCH;
    else case (state)
      FETCH:   state <= DECODE;
      DECODE:  state <= EXECUTE;
      EXECUTE: state <= FETCH;   // loop back
      default: state <= FETCH;
    endcase
  end
endmodule

Build and run: iverilog -o fsm control_fsm.v tb.v then vvp fsm, and open the dump with gtkwave fsm.vcd. Expected: state steps 0 → 1 → 2 → 0 each clock, cycling forever.

Model response

Hardwired control implements the decode/sequencing directly in logic — it's fast and compact, but every instruction must be baked into fixed gates, so it's rigid and hard to extend or fix. Microcoded control stores each instruction as a small program in a control ROM, so adding complex or variable-length instructions (and fixing bugs) is just editing the microcode — at the cost of an extra lookup, hence slower.

Early CISC machines had rich, irregular instruction sets and limited logic budgets, so microcode was the practical way to implement them. RISC deliberately simplified the instruction set to a small, regular form that maps cleanly onto fast hardwired control and pipelining, so modern high-speed pipelines lean hardwired.
